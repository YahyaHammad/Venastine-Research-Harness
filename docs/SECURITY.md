# Security Policy

## Supported Versions

| Version | Supported |
|---|---|
| `main` (0.1.x) | Yes — security fixes ship on `main` first |

No long-term support branches yet. If you are on a fork, rebase on `main` before reporting.

## Reporting a Vulnerability

**Do not open a public issue, discussion, or pull request for a security vulnerability.**

**Email the maintainer at YahyaHammad@proton.me**, with the subject `[SECURITY] Venastine — <title>`.

Send a high-level summary first. Do not include full exploit code in plaintext until a secure transfer method has been agreed.

**Or use GitHub Private Vulnerability Reporting, where it is enabled:** *Security* tab → *Report a vulnerability*. It is the better channel when available, because the report, the fix and the advisory stay in one place — but it is a public-repository feature, so email is the channel that always works. Use email if you do not see the button.


### What to include

* Affected file(s) and line(s) — e.g. `security/sandbox.py:134`, `tools/registry.py:187`
* The concrete trigger — not "could be a problem" — the exact call, config (`ToolPermissions.shell=True`, `providers.json` entry), and filesystem/network/model state that reaches it
* Whether you can reproduce it offline (`python -m pytest -q` or a minimal script) and the commit you tested against
* Impact — what an attacker gains (exfiltration, code execution, bypass of approval, etc.) and whether it needs a local `shell` opt-in or is reachable on a default install

A minimal reproduction is not required, but it makes triage much faster.

## What to expect

* **Acknowledgment** within **2 business days**.
* **Triage and initial assessment** within **7 days** — we will confirm severity (`S1`–`S4` per `#15` tracker), whether it is in scope, and whether we need more info.
* **Fix and disclosure** under **coordinated disclosure with a 90-day window**:
  * We will develop and test a fix on a private branch.
  * We will ship the fix to `main` and tag a release as soon as it is ready — often well before day 90.
  * Public disclosure (advisory + `DEVLOG.md` entry + `tests/BREAKING_CHANGES.md` row) happens **7 days after a fix ships to main** (to allow users time to update), or **90 days after your initial report**, whichever comes first, unless extended by mutual agreement.
  * If you prefer, you will be credited in the advisory and `DEVLOG.md`; if not, you will remain anonymous.

We will keep the private thread updated at least every 14 days until resolution.

## Scope

In scope (examples):

* Bypass of `security/permissions.py` / `safety/policy_enforcement.py` (approval, `is_tool_allowed`, `requires_approval`, `check_output_policy`, blocked domains, secret redaction)
* Sandbox escape or network egress from a tier that should not have it (`security/sandbox.py`, `security/capability.py`)
* Workspace trust boundary bypass (`core/workspace_trust.py`, `core/config_loader.py` tier precedence)
* Credential exfiltration via tool arguments/results, logs, or `param_digest` display
* MCP `autoApprove` / `mcp.json` trust bypass

Out of scope: social engineering, physical access, compromise of a provider's own API, vulnerabilities in upstream dependencies without a harness-specific trigger, or issues that require `tool_permissions.shell: true` together with `shell_approval_mode: never` *and* are already documented as deliberate. `README.md` § *"`shell` is classified, not just approved"* records that `never` "is the old unbounded behaviour, kept on purpose" — in that mode `cat ~/.aws/credentials` runs on the host unprompted, and reaching it takes writing the word `never` in `config.yaml`. We still want such a report, but it will be closed as documented risk. The same holds for `shell_approval_mode: contained` (§48, CE2), within its narrower scope: any command the container confines runs unprompted when it gets no network, code included, so what that code reads inside the workspace -- a `.venastine/` directory among it, when the workspace contains one -- and what it tries against the container boundary are documented risk. Network egress and reads outside the workspace still ask in that mode, and a report of either reaching a model unprompted is in scope.

The same applies to `allow_insecure_sandbox_fallback: true` **together with** `auto_approve_sandbox_fallback: true`. That pair is unprompted arbitrary code on the host, with your own file access, including writes into the harness's own source tree — and the harness ships as a folder of Python, so a run can edit the code the next run executes. It is not defended against, and the reason is that it cannot be: an uncontained host shell cannot be bounded from inside the same process. A path check stops `echo x > ../config.yaml` and a `python -c` payload walks straight past it, which is a control that reads as safety without being it. The container is the boundary, whether Docker or Podman runs it. `README.md` § *"`shell` is classified, not just approved"* states the same thing at the point of use.

**Since batch 40 these settings are read ONCE, at startup, into a frozen posture
(`security/posture.py`).** Before that they were read live at every decision, so
`config.SHELL_APPROVAL_MODE = "never"` -- a single attribute assignment -- turned the shell gate off
for the rest of the process from anywhere in it, and `os.environ["VENASTINE_REDACT_OFF"] = "1"` did
the same for credential redaction. The posture now cannot be changed by a tool call, a settings
file, an environment variable, model output, or a TUI command; each of those is pinned by a test in
`tests/test_posture.py`.

It **can** be changed by arbitrary in-process Python, which can also rebind the accessor itself. A
frozen dataclass raises where a bare assignment succeeded, which raises the bar without closing the
class. In scope: any route from model output or repository content to a changed posture. Out of
scope: "I achieved arbitrary code execution and then changed it", which is a report about the
execution.

Note that all of these settings live in `config.yaml` (`shell_approval_mode`, `tool_permissions`, and the two `*_sandbox_fallback` flags) — none has a `settings.json` key or an environment override, by design, and `config.yaml` itself has exactly one location and no override variable. Keys rather than line numbers because the three this sentence used to cite had all gone stale. What IS in scope, and was fixed rather than documented: a sandboxed command reaching the harness's install tree or `~/.config/venastine/` through the workspace mount (`security/protected_paths.py`), and any argument spelling that makes the classifier and the executor disagree about where a token ends. **That first claim is about the CONTAINER route, and it is stated narrowly on purpose:** a command running under the optional WSL backend (`allow_wsl_backend`, shipped off) reaches both -- measured, the harness's own `config.yaml` and `~/.config` are writable from the distribution -- which is why a WSL command naming a protected segment is refused outright rather than asked about, and why the backend is on the startup banner and the sidebar badge for as long as it is enabled.

**The project's `.venastine/` directory is guarded by `PROTECTED_SEGMENTS` (`security/protected_paths.py`), one list with three consumers.** The `read`/`write`/`edit` tools hard-refuse any path resolving into the segment — pre-approval via `refusal_check` and again in the handlers, whatever the approval booleans and the workspace boundary say. A shell command whose tokens name the segment always requires approval under `tiered` mode, before the fallback opt-in and the capability rule can answer for it; when approved it still runs contained, where the read-only bind of `.venastine/` (§28 G6) is the write backstop. What remains documented risk: the shell check is a token check and does not parse (G2), so a spelling carrying no literal segment — a glob prefix like `.ven*/settings.json`, or a variable assigned outside the checked tokens — is not caught by it; on the auto-approved INERT tier that cannot matter, because EP5 executes argv with no shell and the tokens are the arguments, and under the shipped `tiered` mode every tier that could expand one is asked about anyway. That last clause was false until §48 (CE1): a contained command was auto-approved, so `cat .ven*/settings.json; true`, or a `python -c` that opens the file, read it with no prompt. Under `contained` and `never` it is still not true -- such a command runs unasked, the read-only bind stops a write, and the read is documented risk. `SHELL_APPROVAL_MODE = "never"` remains the opt-out it always was, and MCP servers exposing their own file tools are a separate surface this list does not reach.

**WSL is an opt-in backend with no isolation, and is described as one (ROADMAP_v3 §49, slice 3).** With `allow_wsl_backend: true` the agent may ask for a command to run in a WSL distribution instead of the container, per call. It is not a weaker sandbox; it is the user's own machine with a Linux userland on it. Measured, and stated here rather than left to be discovered: the harness's own `config.yaml` is writable from there, `~/.config` is writable, there is no memory, CPU or process limit because those belong to the whole WSL VM, the network is always on, and Windows interop is a kernel feature that survives an emptied environment -- so a WSL command can start `cmd.exe` with the user's full Windows authority and no argv or environment choice prevents it. What the harness does hold: `containment_for` answers UNCONTAINED for every tier, so under `tiered` and `contained` only a read-only command whose every argument is inside the workspace runs without a prompt; a command naming a protected segment is REFUSED, not asked; the process is started with the scrubbed environment, which drops `WSLENV` and so stops the one mechanism that carries a named Windows variable's value into the distribution; and the workspace is translated by `wslpath` rather than by `wsl.exe --cd`, which answers an untranslatable path by exiting 0 and running somewhere else. In scope for a report: any route from model output to a WSL command that was not approved under these rules. Out of scope: that an approved WSL command can do what the user can do, which is what the backend is.

**SSH is an opt-in backend on a machine this harness cannot inspect, and NOTHING there runs without asking (ROADMAP_v3 §49, slice 4).** With `allow_ssh_backend: true` the agent may ask for a command to run on the one host configured in `config.yaml`, per call. The rule that makes it different from every other backend: no command is auto-approved on this route, not even a read-only one, and that is not caution but arithmetic -- the check that decides whether a command's arguments stay inside the workspace resolves them against the LOCAL filesystem, so on a remote it is answering a true question about the wrong machine. Slice 3 is the evidence for what such a check is worth: a path test that cannot resolve does not fail loudly, it approves confidently. What the harness holds: authentication is a key file or a running `ssh-agent` and **this harness never asks for, holds or stores a passphrase or password** (`BatchMode=yes` is passed for that reason -- measured, without it `ssh` waits indefinitely to prompt on a terminal this process does not own); the host key is PINNED in `config.yaml` and a key that CHANGES is refused rather than accepted; `-F none` stops the local `ssh` reading a per-user config that could carry `ProxyCommand` or `LocalCommand`, from a path this harness cannot redirect; the command crosses ONE quoting boundary and runs under `bash --norc --noprofile -c`; a command naming a protected segment is REFUSED, because `ssh localhost` is this machine and nothing here can tell that it is not; and the backend is on the startup banner and the sidebar badge for as long as it is enabled. Two behaviours are disclosed rather than fixed, both measured: **a kill does not reach the remote command** -- ending the local `ssh` leaves the far side running until its in-guest `timeout` fires, and the pty that would deliver a hangup also merges stderr into stdout and rewrites every line ending, so it is not used -- and **`write` saves locally while the shell runs remotely**, so a file the agent just wrote is not there. In scope for a report: any route from model output to an SSH command that ran without the approval these rules require. Out of scope: that an approved SSH command can do what the configured credentials can do, which is what the backend is. **Slice 5a amends one sentence of the above and nothing else:** the harness CAN now hold an SSH key passphrase and an account password, if you put them there -- see the paragraph below -- and when it does, `BatchMode=yes` is replaced by `SSH_ASKPASS_REQUIRE=force`, which keeps the same property by a different mechanism (every prompt goes to a helper that answers at once and cannot block). With nothing stored the connection is byte-for-byte what slice 4 shipped.

**The harness-held secret store is encrypted at rest and opened once per session (ROADMAP_v3 §49, slice 5a).** `/secrets` (or `--secrets` on the CLI) keeps named values -- an SSH key passphrase, an SSH account password, and from slice 5b a sudo password -- in `~/.config/venastine/secrets.json`, sealed with AES-256-GCM under a key derived from a master passphrase by scrypt. **What that defends against, precisely:** the AGENT reading the file. A shell command on WSL, on SSH or on the host fallback can `cat` it and gets ciphertext, which is the threat this harness actually has; it also survives a backup, a sync client or a stolen disk. An OS keystore was rejected for exactly the property that makes it convenient -- DPAPI and its siblings decrypt for any process running as you, and the agent's own shell is such a process. **What it does NOT defend against, stated because a half-understood control is worse than none:** arbitrary in-process Python, which this document already concedes defeats the frozen posture too; anything watching you type the passphrase; and a crash dump taken while the store is open -- the plaintext is held in a buffer that is zeroed on lock, but CPython hands out immutable copies nothing can reach, so that shortens a window rather than closing one, and it is measured rather than assumed. The plaintext is in process memory and nowhere else: never on disk, never in an environment variable, never in an argv, never in a log -- four properties with a test each. It is dropped on `/secrets lock`, on quit, when an exception escapes anything using a secret, when the askpass listener sees a token it did not mint or a prompt nobody measured, and when the file changes on disk underneath the process. A value the harness holds is stripped from tool output **whatever `redact_tool_outputs` says**, because that switch governs guesses about other people's credentials and this is the harness leaking its own. Reaching `ssh`, a secret crosses on a loopback connection authenticated by a single-use token rather than in `ssh`'s environment, which any process running as you can read; the honest limit is that someone able to read that environment gets the token and could then race the helper during one connection, which is narrower than a value sitting there at rest and is not a boundary. A stored credential the server REFUSES is quarantined for the rest of the run rather than retried, because one refused call makes two authentication attempts and retrying every command would walk a real account into a lockout. In scope for a report: any route by which a stored value reaches the model, the transcript, the database, a log or a subprocess environment. Out of scope: that someone who already runs code in this process can read what this process holds.

**A command can be run as root, and every one of them asks you first (ROADMAP_v3 §49, slice 5b).** A tool call may set `needs_root`; the harness then prefixes `/usr/bin/sudo -k -S -p '' --` and supplies the password stored for that machine. **It runs on WSL and over SSH and nowhere else.** The container is refused because a command there ALREADY runs as root and the image ships no `sudo` at all, so a prompt would be about a privilege the command already has; the host fallback is refused because on Windows `sudo.exe` elevates through a UAC consent dialog that cannot take a password on stdin, which is a different mechanism and a separate measurement rather than an assumption. **A root command always meets a human**, above both opt-ins and in every approval mode but `never` -- and that is a correction rather than a restatement, because the gate was measured auto-approving `sudo apt-get install` on WSL whenever `auto_approve_sandbox_fallback` was on. The step fires on the declaration OR on the command naming `sudo`, `doas`, `pkexec` or `su`, since a model that types `sudo` itself never sets the flag; it is a token check and refuses to parse, so a command that merely mentions the word costs one prompt. **The password goes on stdin and nowhere else** -- not in an argv, not in an environment, not in a log, not in the result, each asserted against a real run -- and the command behind `sudo` cannot read it either, because its stdin is explicitly closed. That last control is there because of a measurement and not a theory: `sudo -S` reads stdin only when it must authenticate, so on a host with a passwordless rule it reads nothing and the password would be the command's own input. That was reproduced on two different `sudo` implementations, with the `-k` flag and without it, which is also why `-k` is documented as buying one authentication per approval and nothing more. **If no password is stored for that machine the call is refused outright**, naming the entry to create: the stored secret is what turns root on at all, and there is deliberately no separate config flag for it. A refused password is not retried for the rest of the run, because `sudo` allows three attempts a call and a retrying agent could walk a real account into a lockout on a host that counts them. In scope for a report: any route by which a root command runs without a human answering, or by which the sudo password reaches the model, a log, an argv or a command's input. Out of scope: what root can do on a machine once you have approved it -- that is the privilege you granted, and the prompt says so in those words.

**Background sessions (ROADMAP_v3 §49) run under the same gate and the same backends as `shell`.** A session is a shell command that outlives the call which started it, so it is classified, approved and routed by exactly the rules above: `shell_background` and `shell_monitor` are registered with `shell`'s own approval check, and `tool_approvals` has no key for either, for the reason it has none for `shell`. Three properties are worth stating because they are what a long-lived command adds. **Session output is kept in memory only** -- a first and a last span of characters, with the middle dropped and reported as a gap -- and never written to disk, because program output can carry secrets, redaction is pattern-based, and a file would be a durable copy of whatever the patterns miss. **A session's container carries a label naming the process that started it and an in-container `timeout`**, so it dies with its harness, or shortly after it when the harness dies first, and one instance's exit cleanup cannot reach another's containers. **And a session can only be started by a run something will wake when it reports** — a chat turn or a subagent — which is what stops an unattended research pass starting work that nothing would ever report, read or stop.

## No bounty

This is an independent research project with no funding — **we cannot offer monetary rewards, bounties, or swag.** We will credit you publicly if you want, and we will prioritize a fix. If you need a bounty, please use a third-party program that covers this repo, or treat the report as a voluntary disclosure.

## Disclosure and credit

* We will publish a GitHub Security Advisory (GHSA) 7 days after the fix ships to main (or at the 90-day mark), requesting a CVE if the severity warrants it.
* We will not disclose your identity without permission.
* Please do not disclose the issue publicly (including in a fork, gist, or write-up) before public disclosure or advisory publication — this protects users who have not yet updated.
